
### Тикеты
* Согласование с владельцем процесса
* Согласование с тем кого добавляем в процесс
* Если один раз задача вернулась по эскалации - звоним, второй раз к начальнику
* Всегда в задачах указываем важность, эпик, стадию
* Оля фиксирует цель запроса, расшифровывает запрос,  ставит статус "Постановка ТЗ"
* Паша пишет как именно решать запрос, ставит статус "Программирование"
* Программисты берут задачи только со стадии "Программирование"
* Оргструктуру меняем только в отдельных процессах
* Согласование изменения задачи по процессу с ответственным за зону. Ответственный по новым правилам прописывается в паспорте процесса. Если нет паспорта, то действуем так: если исполнитель задачи 
* Руководящая должность, то согласовываем с исполнителем. Если исполнитель задачи - не руководящая должность, то согласовываем изменение с руководителем исполнителя задачи. 
* Если запрос в сервис elma требует интеграции с другими ИС, то ставим задачу на доработку разработчикам сопряженной ИС, в которой фиксируем запрос-основание. В тикетах для elma фиксируем ссылку на запрос на интеграцию. Стадия тикета elma при ожидании разработки в сопряженной ИС 
* "Контроль", статус - backlog. По получению результата интеграции тикет elma выводится из elma и переводится в стадию "Программирование".
* Запросы на создание нового процесса в elma. Первая итерация - отправка инициатору анкеты на процесс для заполнения. Помощь инициатору с заполнением анкеты, внесение предложений по процессу инициатору. После сформированной анкеты Оля составляет паспорт процесса.
* Последовательность работ со стороны ОИТ нужно обсуждать. После анкеты паспорт или сначала согласование описанного процесса со всеми участниками процесса? Или же сначала прорисовка карты процесса?

### Процессы
* Комментарии обязательные спрашиваем только когда процесс отменяется, происходит отказ.
* Комментарии на согласование не спрашиваем
* Если есть поля для замечания, комментарий не спрашиваем
- комментарий на кнопке перехода может быть, если возвращаемся по процессу или передаем на уточнение. 
- Наименование обязательно поля на кнопке перехода должно носить смысловую нагрузку согласно кнопке перехода. Должно быть описано в паспорте процесса
- необязательные комментарии убираем c кнопок переходов 
- наименование поля для замечания в лист согласования должно во всех процессах называться одинаково 
- в процессе пользователь явно выбрать пишет он замечания в лист согласования или ставит значение "б/з"
- ПАСПОРТ дает легитимность, содержит подписи, но не актуальные изменения
- актуальные изменения процесса видно на карте процесса в табличке с названиями задач, переходами с задач, группами зоны ответственности задач. Эта штука генерируется автоматически ночью бфтаймером
- Выход с таймера - комментарий в процесс
- Если комментарий обязательный - значек 💬 



### Карта
* Направление движения: Слева на право, сверху вниз
* Не должно быть пересекающихся линий, насколько это возможно
* Зоны ответственности группами
* Скрипты на карте только необходимые
